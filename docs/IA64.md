## Open issues

1. **Cleared (2026-10-18, the user's report): large API responses were truncated or
   stalled.** The user found Logical names on `LNM$SYSTEM_TABLE`, the failing case,
   working again. Not re-tested from here (the curl test needs a signed-in session),
   and what fixed it was not recorded; if it comes back, the next steps below still
   apply. What was seen: a 63 KB
   logical-name listing, signed in as STEWARD_TEST: through the proxy 2 of 5 stopped
   1,018 bytes short (curl exit 18; Firefox `NS_ERROR_NET_PARTIAL_TRANSFER`) and 1
   stalled at 32 KB for 120 s; straight to lighttpd on 8443, 1 of 5 short by the same
   1,018 bytes, times 9 to 75 s. Through `api_probe` the same request is complete in
   under a second, and a 26 KB static file comes through lighttpd whole. Not the proxy;
   not Steward's socket code (`send_all` loops on partial writes and the close is
   orderly). Left: lighttpd's own sending on IA64 (the vms-lighttpd I64 build and its
   TCP/IP), or lighttpd reading FastCGI from the pool. The same Steward behind x86's
   lighttpd does not do this. Next steps:
   - a ~200 KB static file in `SYS$SYSDEVICE:[VMSLIGHTTPD_DATA.HTDOCS]`, fetched a
     few times on port 981 from the LAN: short or stalled means lighttpd itself (a
     vms-lighttpd issue);
   - if that comes through whole, a FastCGI client probe on the node against the pool's
     port (19300), to show the pool's side complete.
   **The user's observation (2026-10-16):** with the machine quiet, every page performs
   well and the only failure is Logical names on `LNM$SYSTEM_TABLE`
   (`%STEWARD-F-NOSERVER`). That is the largest response Steward sends there (63 KB
   for STEWARD_TEST, more with privileges), which fits a fault that depends on size.
   A useful test: other large responses (a long user list, the full process list
   with WORLD) should fail the same way if it is size, not the table.
2. **Logical-name listings were slow while the node was busy**, 3 to 10 s, where
   `api_probe` takes under 1 s: each listing creates the D14 helper process. On a quiet
   machine the user found performance fine across the board (2026-10-16), so this is
   load, not a problem of its own; measure again now that issue 1 is cleared.
3. **lighttpd's logs cannot be read while it runs:** TYPE and CONVERT/SHARE give
   `RMS-F-ORG`, sftp "not a regular file". The diagnosis above had to go without them.
   A vms-lighttpd matter.
4. **`vms.sh` sometimes fails to start its procedure on IA64** (the ssh session ends
   at once, printing nothing; about six times in the live tests). It now retries and
   reports ssh's exit status; the cause is not known. Tooling only.
5. **Not yet exercised on IA64:** a password change and the expired-password flow
   through Steward (they change the password, and history then refuses a change back;
   do them in the browser check with a password set afterwards), and the 5 s budget on
   the SSH log search (only in the stub).
